# EPIC-0003 voice A1c: operations — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Work in the five batches of "Execution batches" below, with the three independent reviews it names.

> Story: proposed **US-0072** (EPIC-0003, High, L), filed in Task 0 from `docs/ID_REGISTRY.md` (the number is a proposal, not reserved: if the registry has moved, every `US-0072` below shifts with it, and so do the TASK, AC and TC numbers). Branch: `feature/EPIC-0003-US-0072-voice-operations`, cut from `origin/develop` after this plan's docs PR has merged (A1a and A1b are on `develop`: PR #130, squash 76a61c0; PR #132, squash 63a4554; status commit ebceb50). TDD per task: write the failing test, run it and see it fail for the stated reason, then the code. A test marked **(characterisation, expected PASS)** pins behaviour that already holds today: it must pass before any code change and stays as a regression guard.

**Goal:** One command, `pnpm voice:up`, brings up the voice infrastructure on the pilot laptop (a hardened native whisper-server on loopback, then LiveKit and the TLS proxy from `deploy/compose`) with real LiveKit keys generated into `.env` only when absent; `pnpm voice:check` reports whether everything a voice session needs is in place without printing a secret; `pnpm voice:down` stops everything `voice:up` started; the web server is loopback-only behind the proxy; a LiveKit outage no longer turns voice off for the rest of a session; and the owner has a runbook with the room-test script. Voice stays dark behind `VOICE_ENABLED=0`.

**Architecture:** A new workspace package `services/voice-ops` (`@acr/voice-ops`, TypeScript, no runtime dependency beyond `node:` built-ins and the workspace `@acr/adapters`) holds the three commands as small modules behind injected seams (command runner, detached spawn, file system paths, network and DNS lookups, clock, timers), so CI tests every decision without Docker, LiveKit or Whisper; the root `package.json` gains `voice:up`, `voice:down`, `voice:check` and `voice:timings` scripts in the existing `pnpm -s --filter <pkg> <script>` style. `deploy/compose/voice.yml` adds a `livekit` service (always) and a `caddy` service (profile `lan`) under a fixed project name, each pinned by digest, LiveKit with its keys only from a private env file in the voice state directory and its API on `127.0.0.1` only. Control's `VoiceHost` stops counting a worker exit as a fault when the exit is a LiveKit loss and control's own probe of `LIVEKIT_HOST` finds LiveKit unreachable: voice is then "unavailable" (not "off"), control probes on a capped backoff (2 s doubling to 30 s) and restarts the worker when LiveKit answers, with one facilitator alert per outage and one on recovery; every other exit still spends the five-try budget.

**Tech Stack:** TypeScript, pnpm workspaces, Node 22 (`node:child_process` `execFile`/`spawn` without a shell, `node:net`, `node:dns`, `node:tls`, `node:crypto` `X509Certificate` and `randomBytes`, `fs.statfs`, `node:util` `parseEnv`, global `fetch`), Vitest, Playwright 1.64 (one bind test), Docker Compose v2 (installed: Docker 29.8.2, Compose v5.5.0; not run by this plan), whisper.cpp `whisper-server` 1.9.5 (Homebrew), images `livekit/livekit-server` (1.13.11 proposed) and `caddy` (version chosen in Task 0). **No new npm dependency.** The optional DNS-challenge path (Task 13) needs a custom Caddy build with one DNS provider module: a new dependency, built only after the owner chooses it.

**Spec:** `docs/superpowers/specs/2026-11-08-voice-part-a-design.md` (Draft 3, owner answers in section 16; sections 9, 11, 12, 13, 14 are the ones this slice implements). **Master plan:** `docs/superpowers/plans/2026-11-08-voice-part-a-overview.md` (settings, C9, release gate). **Previous slices:** `docs/superpowers/plans/2026-11-08-voice-a1a-pipeline.md`, `docs/superpowers/plans/2026-11-08-voice-a1b-livekit-consent.md` (K1 to K13, D1 to D63, the batch 4 notes on the restart budget). Where this plan differs from the outline, the overview or the spec, "Resolved Facts" and "Contradictions" below give the exact change.

## Restart budget: the decision

Read `services/control/src/voice/voice-host.ts:160-210,389-404`, `restart.ts` and the A1b batch 4 notes (D13 to D22). **Chosen design (Tasks 10 and 11):**

| Worker exit | LiveKit ingest and a probe | Probe of `LIVEKIT_HOST` | Effect |
| --- | --- | --- | --- |
| code 3 (`EXIT_LIVEKIT_LOST`) | yes | no HTTP answer within 2 s | **Outage.** Not counted (`failures` unchanged, neither raised nor reset). `mediaLost = true`; `voice_availability { available: false, off: false }`; ONE `livekit_lost` alert (closes an open voice turn like `worker_restarting`). Control probes again after `livekitRetryDelay(n)` = min(30 000, 2000 x 2^(n-1)) ms: 2, 4, 8, 16, 30, 30, ... s; no worker runs meanwhile. When a probe answers: `mediaLost = false`, ONE `livekit_recovered` alert (info), a new worker is spawned (not counted); availability follows its `worker_ready` as today. |
| code 3 | yes | any HTTP answer, or the probe rejects | Counted, exactly as today (`workerFailed`). |
| code 3 | no (file ingest, or no LiveKit) | — | Counted. |
| 0, 1, 2, `null` (signal) | any | not probed | Counted. |

Kept: a spawn that throws counts; `voiceOff`, an ended session and control's shutdown stop everything (pending probe timers are cancelled and a late probe answer is ignored); `attach` spawns nothing while `mediaLost` or a probe is pending and tells the new runtime `available: false`; `available` gains `&& !mediaLost`, so pages say "Voice is not available right now. Use the text box." for the whole outage without flapping. Why a probe and not the exit code alone: R4 and K7. Why no cap on outage retries: an outage costs nothing but a loopback GET every 30 s and the session keeps running by text; a misconfigured LiveKit that answers HTTP but refuses every room still reaches voice off within the five-try budget. Why 2 s first: a LiveKit container restart takes seconds, so voice comes back about as fast as before for short blips.

## Global Constraints

- Every A1a and A1b invariant holds: no change to the session log format, `LOG_FORMAT`, the consent file, the voice record or any event; `VOICE_ENABLED` defaults to `0` and **`voice-ops` never sets it, `CONSENT_NOTICE_VERSION` or `SPEECH_INGEST`** (it prints what an operator must set, and that voice stays pre-production only); the privacy invariant (A1b Global Constraints) is unchanged.
- **Secrets are never printed, logged or put in an argument list:** `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, the `STT_URL` request path, `VOICE_DNS_API_TOKEN`, any `.env` value. `voice-ops` output lines are fixed sentences plus non-secret facts (mode, hostname, ports, model label, days to expiry, versions, check levels). A test scans every command's output, and every argument list given to the command runner, for the secrets of its fixture `.env`.
- **`.env` writes:** only names that are absent are added, as one appended block; an existing value is never changed; the file is read through one descriptor opened with `O_NOFOLLOW`, must be a regular file owned by the user with no group or other permission bits, and is replaced atomically (an `O_EXCL` 0600 temp in the same directory, fsync, rename, directory fsync); a symlink, a missing file, a group- or world-readable file, a half key pair, an empty assignment of a managed name and the public development keys (`devkey` / `secret`, any case) are refused with the file unchanged byte for byte.
- **Generated values:** `LIVEKIT_API_KEY` = `API` + 24 hex (12 random bytes); `LIVEKIT_API_SECRET` = 64 hex (32 random bytes); the STT request path = `/` + 32 hex (16 random bytes); all from `crypto.randomBytes`.
- **whisper-server is always started as** `whisper-server --host 127.0.0.1 --port <port> --request-path /<32 hex> -m <STT_MODEL_FILE> -sns --public <empty 0700 directory in the state dir>` and **never with `--convert`**; nothing calls `/load`.
- **LiveKit:** never `--dev`; keys only from `<VOICE_STATE_DIR>/livekit.env` (0600, `LIVEKIT_KEYS=<key>: <secret>`), never `env_file: ../../.env`; API port `127.0.0.1:7880:7880`; `node_ip` = the LAN address in `lan` mode, `127.0.0.1` in `local` mode; media `7881/tcp` and `7882/udp` on that address only; `logging.level: warn`.
- **Caddy (`lan` profile):** `admin off`, no `log` directive, no `trusted_proxies`, no `X-Forwarded-For` header directive, owner-supplied `tls <cert> <key>` (read-only mounts), the LiveKit site forwards `/rtc*` only with `header_up -Cookie`; ports on the LAN address only.
- **Images pinned by digest** (`image: name:tag@sha256:...`), the compose project name fixed to `scenecoach-voice`; `voice:up` starts nothing it cannot stop: the state file is written before anything is started and updated right after each start; a failure after a start rolls back what was started.
- **State directory:** `VOICE_STATE_DIR` (absolute; default `<HOME>/.scenecoach/voice`, never inside the repository), mode 0700, owned by the user, not a symlink; files 0600: `state.json`, `livekit.env`, `whisper.log`, `public/` (empty).
- No new npm dependency; `voice-ops` imports only `node:` built-ins and `@acr/adapters` (root index). No regular expression with a letters-digits-underscore class (id-rule guard, R13): hex, hostnames and addresses are checked character by character.
