# US-0080 notes: scene objective, end rule and the scene-ended dialog

Story: **US-0080** "Players see each scene's objective and end rule, and a dialog when a scene ends" (EPIC-0002 demo feedback fixes), task **TASK-0120**. These notes hold what the owner folds into `docs/RELEASE_PLAN.md`, `docs/TEST_CASES.md`, `docs/ID_REGISTRY.md`, `CHANGELOG.md`, `docs/THREAT_MODEL.md` and `docs/ROLLBACK.md`; none of those files was edited on this branch.

## Acceptance criteria

- [x] AC-0460: A scene in `script.yaml` may carry an optional `ends_when`: one plain-language line, trimmed, 1 to 200 characters, no control characters (line breaks included). A scene without it loads with no such key. (`packages/script/src/schema.ts`)
- [x] AC-0461: A scenario that does not use `ends_when` keeps the same canonical scenario hash, so a session in progress against it still resumes. Proven by pinned pre-change hashes (`scenario-hash-ends-when.test.ts`).
- [x] AC-0462: The rule text a player sees is resolved on the server: the scene's `ends_when`, else its first `gm_detects` condition that passes the same rule, else none (`sceneEndsWhen`, `packages/script/src/ends-when.ts`).
- [x] AC-0463: A player's `joined.scenes` entries carry an OPTIONAL `endsWhen` (built field by field in `SessionHost.plainScene`, absent when there is no rule); only the player's own scenes, never another role's. The browser picks scene fields one by one and drops a non-string or over-200-character `endsWhen`. The facilitator console carries it too (BFF `consoleScenes`, browser `toScene`).
- [x] AC-0464: The player's scene card shows "Objective: <goal>" prominently (its own `objective` class, no longer the small muted "Goal:" line), "Ends when: <rule>, at N min, or when your facilitator moves on" under it (only the time box and the facilitator when there is no rule), and the time left as before. The console's live view uses the same card.
- [x] AC-0465: When the live page receives `scene.exited` with reason `gm_detects`, `time_box_elapsed` or `facilitator_advance`, an inform-only dialog opens: "Scene N of M has ended: <title>", the reason in plain words ("The Game Master judged this scene's goal was met: <rule>." / "Time ran out (N min)." / "Your facilitator moved the session on."), and "Next for you: Scene K of M: <title>" with its objective and end rule, plus whether it has started or "starts when the session reaches it" (a next scene the player is not in may run first). After the player's last scene, while the session goes on, it says so. A Continue button closes it.
- [x] AC-0466: The dialog is not modal: the next scene runs underneath (the scene clock and the AI do not wait), the transcript and updates keep arriving, the say box stays usable and keeps a typed draft. The focus moves to Continue only when nothing holds it and the say box holds no draft; Escape closes it from anywhere on the page; on close the focus goes back where it was, else to the say box. `role="dialog"`, `aria-modal="false"`, labelled and described; a polite status region announces the title and the reason.
- [x] AC-0467: The final scene's end (followed by `session.ended` with `script_complete`) shows the "Session complete" variant: "All scenes are done. The facilitator can now run the evaluation." instead of a next scene. `facilitator_end` (End session) opens no dialog (the existing end banner explains it), and an open dialog closes when the session is ended that way.
- [x] AC-0468: The dialog opens only for a `scene.exited` the live page received (`PlayerView.lastExit`, set by `applyPlayerEvent` only; `initPlayerView` never sets it), so a late join or a reload shows none.
- [x] AC-0469: Every scene of `friday-escalation` and `friday-escalation-extended` has an `ends_when`; scenes 2 and 3 of both scenarios gained an `opening_inject` addressed to exactly the players of that scene (never `client_sponsor`); rubrics are byte-identical as before; the demo counts are unchanged (29, 14, 42, 14). Scenario `version` fields are NOT bumped: no test, calibration stamp or guard requires it (the stamp keys on the rubric hash and prompt version; `scenario-content-us0040.test.ts` still pins 1.3 and 1.1).

## CHANGELOG line (under `[Unreleased]`, `### Added`)

- Players now see what each scene is for and what ends it, and are told when a scene ends (EPIC-0002, US-0080, AC-0460 to AC-0469). The scene card shows the objective prominently and "Ends when: ..., at N min, or when your facilitator moves on". When a scene ends, an inform-only dialog says why (the Game Master judged the goal met, time ran out, or the facilitator moved on) and names the player's next scene with its objective and end rule; the next scene is already running underneath, and a message being typed is kept. After the last scene the dialog says the session is complete and the facilitator can run the evaluation. Scenario authors can give each scene an optional plain-language `ends_when` (otherwise players see the scene's Game Master condition); a scenario without it keeps its hash. Both Friday Escalation scenarios gained an `ends_when` for every scene and an opening message for scenes 2 and 3. Deploy the control service (runtime) before the web app (docs/ROLLBACK.md).

## THREAT_MODEL notes (proposed addition, "Scene end rules for players, US-0080")

- **What a player newly learns:** the end rule of the scenes they take part in. With no `ends_when` this is the scene's `gm_detects` condition, which until now only the Game Master and the facilitator saw. Owner decision B with fallback A accepts that: a condition is a statement of the scene's goal, not a hidden fact. Authors who want to word it differently, or keep it from players, write an `ends_when` (it always wins). A condition that would fail the `ends_when` rule (empty, longer than 200 characters, more than one line) is not shown at all.
- **Allowlisted copies:** the runtime builds the player scene copy field by field (`plainScene`, never a spread of the scene), only for the player's own scenes (`scenesFor`); the BFF forwards `joined.scenes` as the runtime projected it (unchanged rule) and the browser now picks each scene's fields one by one (`toScene` in `use-session.ts`), so an extra key from a newer runtime is dropped. The console copies pick `endsWhen` too. The leak test (`ws-server.scenes.test.ts`) gained a `PRIVATE-RULE` marker for a scene the player is not in; the wire-contract test (`hub.runtime.test.ts`) pins the new optional key.
- **Rendering:** `endsWhen` is React text (no markup; a test renders a rule with an `<img onerror>` and a `<script>` as text); control characters are refused at load, and the browser drops a non-string or over-200-character value.
- **Event stream:** no new event or field. `scene.exited` already reached players for their own scenes (default-deny `viewFor` unchanged); the reason was already on it. The dialog reads only the live stream.

## ROLLBACK notes (proposed `docs/ROLLBACK.md` section "US-0080")

- **Wire change:** one OPTIONAL field, `endsWhen` on each entry of `joined.scenes` (player and facilitator joins). No log format change, no new event, no change to `session.started`, seats, consent or reports.
- **Deploy order:** the control service (which runs the runtime children) BEFORE the web app. A new web app against an old runtime gets no `endsWhen` and shows "Ends when: at N min, or when your facilitator moves on", and "The Game Master judged this scene's goal was met." without the rule; an old web app against a new runtime ignores the field (it shows the old "Goal:" line and no dialog). Either order works; runtime first gives players the full text from the first page load.
- **Scenario hash:** the Friday scenarios' content changed (new `ends_when`, new opening injects), so their canonical hash changed. **A Friday Escalation session that is in progress when the new scenario files are deployed will not resume after a restart (`scenario_mismatch`)**; deploy between sessions. Any other scenario (no `ends_when`) keeps its hash (TC-0242).
- **Rolling back:** revert the code and the two `script.yaml` files together. An old build given the new `script.yaml` files still loads them (its zod scene schema strips the unknown `ends_when` key) and plays the new opening injects, but its scenario hash differs from the new build's (the key is stripped before hashing), so a Friday session started on the new build does not resume on the old one, and vice versa. Sessions resume only on a build that hashes the same scenario files the same way.
- **Nothing on disk to clean up.**

## Notes for the owner
