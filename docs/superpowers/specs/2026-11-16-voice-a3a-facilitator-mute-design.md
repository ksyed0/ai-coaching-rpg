# Voice slice A3a: the facilitator mutes a participant's microphone (design)

Status: Draft 3 (2026-11-16), after the independent builder check, the owner's two answers (sections 1 and 4) and an Opus review against the code (calls C6 to C11 changed or added by it; the owner asked for the review's changes to be included and the plan written). Story: US-0091 (TASK-0143, AC-0550..AC-0559, TC-0322..TC-0332), filed 2026-11-16. ## 1. Intent and why

During a live session a facilitator can switch off one participant's microphone, and switch it on again. It exists for two reasons the owner named (2026-11-16): **side conversations and background noise** (mostly), and **moderation** (possible). Voice here is used only to make the transcript, which the AI characters and the evaluator then read; the people in the room hear each other in person. So a mute does not silence anyone: it stops what that seat says from becoming game input.

**Decided by the owner (2026-11-16):**
1. Muting is **per seat**, instant and reversible; used during the session.
2. **A line already transcribed before the mute stays.** The log is append-only and sealed; no strike, redact or exclude tool is built now. A mute works going forward only.
3. A3 is split: this slice is **mute only**; live partials are A3b.
4. **A facilitator mute ends only when the facilitator unmutes** (accepted 2026-11-16). A refresh, a rejoin, a reissue or a different person taking the seat all keep it. Simple, fails safe, and a live session and a restart give the same answer; no seat-handover event is needed.
5. **All participants see that a seat is muted** (owner, 2026-11-16: "All participants should see"). Moderation is open to the room, not hidden.

**My calls (to be confirmed by the owner; each is recorded as a call, not a decision):**
- **C1, the route:** a new facilitator command in the existing console command channel, recorded in the session log as `facilitator.command` with `by` (section 4). Not through control and the audio audit log.
- **C2, seat-level persistence:** the facilitator's mute belongs to the seat, not to the holder's connection (owner decision 4 above): it ends only on the facilitator's unmute.
- **C5, what everyone sees (carrying decision 5):** every participant's page shows a notice by role label ("The <role> microphone has been muted by the facilitator" / "... is on again"), never the person's name and never the facilitator's name (`by` stays in the sealed log and the console only). The command is therefore NOT hidden from the players' event stream the way `prompt_ai` is; the builder confirms how `commandForPlayer` passes it and strips `by` for players.
- **C6, before the start:** a mute is allowed before the session starts. It is held in memory and written to the log straight after `session.started`, so it holds from the first turn; a runtime restart before the start loses it (stated residual). Corrected after the Opus review: the log cannot hold a command before the start.
- **C7, ordering:** a mute takes effect on receipt and is rolled back if refused or its append fails; an unmute takes effect only after its append succeeds; the recording check is repeated inside the engine mutex so a line in flight is refused, never appended after the mute (section 4).
- **C8, name:** `mute_seat`, not `mute_voice`, so it is not confused with the participant's `voice_mute`.
- **C9, no Game Master tick** after `mute_seat` (a mute is not a game turn).
- **C10, the muted speaker's refused line** shows the generic `not_recording` notice; the page already explains why.
- **C11, rollback:** `LOG_FORMAT` is NOT bumped (it would block rollback for every voice session). Accepted gaps, recorded in the runbook: a runtime rolled back to before A3a drops all facilitator mutes (re-mute after a rollback), and deploy order is web with or before runtime (an old web console mishandles the new event).
- **C3, the participant is told, and cannot unmute:** their page says the facilitator has muted the microphone, and their own unmute button is off until the facilitator unmutes.
- **C4, shared-secret sign-ins may mute,** with the typed name as `by`, exactly like every other command that goes into the session log. (This differs on purpose from the audio review panel, which refuses shared-secret sign-ins because its audit name had to come from a real account: here the name goes into the log the way all console commands' names do.)

## 2. Goals, non-goals, anti-goals

Goals: the command and its schema in the runtime; the seat state and its effect on recording; the participant frame; the console control in the voice panel; the web command kind; replay of the log restores the state; THREAT_MODEL, VOICE_RUNBOOK, ROLLBACK, CHANGELOG and tracker updates; unit, real-socket and end-to-end tests with mutation checks.

Non-goals: live partial transcripts (A3b); mute all; a timed mute; push-to-talk; striking, hiding or excluding an already-transcribed line; LiveKit-level enforcement (a LiveKit token cannot be revoked and a track mute only affects subscribers; the worker ignoring the track is the effective control); a participant request to be unmuted; deleting past audio (A2b); any change to the participant's own mute.

Anti-goals (a failure even if it technically works): a facilitator-muted seat still recorded, transcribed or logged as a voice line; a participant who gets round the mute by refreshing, rejoining or toggling their own mute; a mute with no `by` in the log; the participant left unaware that they are muted; a mute accepted for an AI seat; the report or evaluator treating the command as something a player said; a mute state silently lost by a runtime restart; a failure to apply a mute that the console shows as muted.

## 3. Constraints

The log is append-only and sealed; a new `facilitator.command` variant must not break any reader of old or new logs (section 4, rollback). `by` comes only from the sealed console cookie (a body carrying `by` is refused), as for every command. Nothing logs a name, a seat or the command text outside the session log itself. The runtime's mute (participant) stays in memory and unaudited; only the facilitator's mute is in the log. Voice off, an AI seat, an unknown seat and an ended session are refused. Control and the speech worker already receive the seat's `recording` flag through `voice_state` and ignore a seat that is not recording; the mute reuses that path and adds no new message to the worker.

## 4. The command and the seat state (runtime)

**Command.** A new `FacilitatorCommand` variant `{ command: "mute_seat", roleId, muted: boolean }` (strict; `roleId` checked as the other commands' role ids; no free text anywhere). Named `mute_seat` (call C8) so it is never confused with the participant's `voice_mute`. Schema entries in `services/runtime/src/host/protocol.ts` and `packages/events/src/events.ts`. `voice_off` and `forbidden` depend on host state, so they are checked in `host.command` before the engine call; the engine's `doCommand` (where `prompt_ai` and `whisper` are validated) only does the role-seat check. It is appended as `facilitator.command` with `by`, like every command. `host.command` schedules a Game Master tick after each command; that is skipped for `mute_seat` (call C9: a mute is not a game turn).

**Ordering (C7, corrected after code review).** Today a command is validated, appended, then applied through subscribers, and the recording check for a `voice_line` runs outside the engine mutex, so a line that passed the check while a mute was queued would still be appended after it. Therefore: a **mute** takes effect on receipt (the seat is marked muted at once and `voice_state` is re-sent) and is **rolled back** if the command is refused or its append fails; an **unmute** takes effect only **after its append succeeds**. The recording check for a `voice_line` is repeated inside the engine mutex (a guard passed to the line append), so a line in flight when the mute arrives is refused, never appended after it.

**Seat state.** The state lives in the shared reducer's `SessionState` (`packages/events/src/state.ts`) as a set of facilitator-muted seats, beside nothing else of the participant's mute (which stays in the host's in-memory `voiceMuted`). Engine restore then rebuilds it from the log, and `PLAYER_SNAPSHOT` (`player-copies.ts`) forces the player projection to be decided at compile time. Every reader of the mute must use the union, not only `isMuted`: `isMuted`, `isRecordingHolder` (`session-host.ts`) and `voiceMutedOf` (feeds `joined.voice` and the `voice` frames) are all changed. Effects, through the existing path: `recording` becomes false and `voice_state` is re-sent; the runtime refuses a `voice_line` for that seat with the existing `not_recording` refusal; the console and every player learn the state (below). Unmute removes the seat and recomputes. The runtime's `forgetVoice` and `release` clear only the participant's own mute, never this set.

**Refusals, in order:** `voice_off` (disabled), `unknown_role` (not a seat of this session), `forbidden` (a seat that is an AI character or otherwise not a human seat), `ended` (the session is over). Allowed while paused. Muting a seat with no holder, or a holder who has not chosen voice, is **accepted** and stored (a mute can only stop recording, so refusing it would fail open). New fixed copy only for `voice_off` and `forbidden`; `ended` has copy already and `unknown_role` keeps the shared generic conflict sentence (changing it would change other commands).

**Lifetime (C2, owner decision 4).** The set is cleared only by a `mute_seat` with `muted: false`. A pause, a resume, a refresh, a rejoin, a reissue and a different person taking the seat all keep it.

**Before the start (C6, corrected).** The log cannot hold a command before `session.started` (restore throws `not_a_session`), and a command carrying a `ref` before the start is refused (`not_started`). So a mute sent before the start is **held in memory** and `start()` writes it as a `facilitator.command` straight after `session.started`, so it holds from the first turn. If the runtime restarts before the start, nothing is kept: that is a stated residual (the facilitator re-mutes), and the console shows the real state.

**Replay (restart).** A runtime restart resumes the session from its log through the engine's restore, so `SessionState` is rebuilt from the `facilitator.command` events: the last `mute_seat` per seat wins. No seat-handover event is read, so a restart and a live session agree. A resumed session comes back paused, as today.

**What everyone sees (decision 5, C5).** The state reaches each audience through existing paths, never `by` or a person's name:
- *Console:* the roster entry gains a facilitator-muted field (roster and `pickVoice` in `console-voice.ts`), so every console view agrees. The roster has no `by`, so the label is a single "Muted by facilitator".
- *Every player:* `commandForPlayer` (`player-copies.ts`) copies listed keys only, so a new case returns `{command, roleId, muted}` and cannot leak `by`; the current state is also in the snapshot / peers roster (`roster.ts`, `peerEntryOf` in `stream-hub.ts`) so a fresh join with no `lastSeq` still sees it. The page must not re-announce mutes it receives as replay of past events, only changes after it connected. AI bots drop the frame (`bot-frames.ts` enum, keep it so); `bot.ts` treats any non-pause command as "resumed", so a test pins that a `mute_seat` does not resume a bot.
- *The muted participant:* a personal frame (below).

**Participant's own mute under a facilitator mute.** The participant's `voice_mute` with `muted: false` is refused while the seat is facilitator-muted (new refusal `muted_by_facilitator`; `muted: true` is accepted and harmless). The `voice` answer, `joined.voice` and every `voice` frame for that seat carry `muted: true` and a new optional `mutedBy: "facilitator"`. This needs: a new runtime push of a `voice` frame to the holder's socket when the facilitator state changes; the web server forwarding an unsolicited `voice` frame as a named event (`stream-hub.ts` currently drops it) and keeping `mutedBy` in `playerJoined`; `muted_by_facilitator` added to `VOICE_SEND_ERRORS` (`stream-hub.ts`) and `VOICE_ANSWERS` (`handlers.ts`) so the page gets the specific refusal immediately instead of a generic error after 2 s. The runtime's `ServerMessage` type (`protocol.ts`) has no schema or version, so the new field is additive.
- *The muted speaker's refused line:* shows the generic `not_recording` notice; the participant's page already says why (call C10: no facilitator-specific notice code).

**Compatibility and rollback (corrected after code review).** Old readers do not crash: the engine's reducers return state unchanged for an unknown command and `event-log.ts` checks only the event type; control's log-tail, report jobs and evaluator transcript do not read commands (no change). Two gaps are accepted and recorded, not fixed, in this slice: (1) a **runtime rolled back to a version older than A3a keeps working but drops every facilitator mute** on resume (the old reducer ignores the command), so the runbook says "re-mute after a rollback"; (2) the web console's `facilitator-copies.ts` `facilitator.command` switch has no default, so an **old web console receiving a `mute_seat` event** returns undefined into its stream; so deploy order is **web with or before runtime**, and the runbook says so. `LOG_FORMAT` is NOT bumped (call C11: it is fixed at `session.started`, so a bump would block rollback for every voice session; the cost is gap (1)). No data step.

## 5. Web server and console

**Web command.** `console-command.ts` gains the kind `mute_seat` with body `{ channel, kind: "mute_seat", roleId, muted }` (strict keys; `roleId` through the existing id check; `muted` boolean), through the existing guard (owner-or-admin, neutral 404), the existing per-cookie or per-account throttle and the existing refusal sentences. `by` comes from the cookie (shared-secret sign-ins use the typed name, C4). New fixed refusal copy only for `voice_off` and `forbidden` (`ended` has copy; `unknown_role` keeps the shared generic sentence).

**Console.** The voice panel's seat table gains a Mute/Unmute button per human seat that has a voice state (`VoicePanelEntry`), word-labelled with one label, "Muted by facilitator" (the roster has no `by`, so "by you" cannot be computed), never colour alone. The console roster gains a facilitator-muted field (`roster.ts`, `pickVoice` in `console-voice.ts`); today it has no mute field at all, so this is new, not an extension. `VoicePanel` deliberately has no live region today, so the polite status line announcing the result is new and designed in the plan; a refused command shows its fixed sentence. The button is a native button with an accessible name naming the seat. Pressing it twice quickly sends one command (in-flight guard).

**Participant page.** The muted participant's voice controls show "The facilitator has muted your microphone" (an `aria-live` notice) and disable the unmute button while `mutedBy` is `facilitator`; when unmuted they return to the normal state and say "You can speak again" once. **Every participant's page** also shows a polite status line by role label ("The <role> microphone has been muted by the facilitator" and "... is on again"), never a person's name or the facilitator's name (C5).

## 6. Approaches considered

- **Route:** (1) a new command in the existing console command channel, logged in the session log with `by` — CHOSEN (call C1): it reuses the one place every facilitator action already goes, gives a sealed audit and the typed name for shared-secret sign-ins, and lets a restart rebuild the state; its cost is a new event variant that old readers must tolerate (section 4); (2) through control with a new parent-channel message and the audio audit log (rejected: a second audit location, a new control route, and shared-secret sign-ins would need a separate decision); (3) ask the participant's page to mute itself (rejected: bypassable, the exact thing the worker must not trust).
- **Where the mute takes effect:** (1) the runtime refuses the seat's lines and reports `recording: false`, so the worker ignores the track — CHOSEN, the existing effective control; (2) revoke or mute the LiveKit track (rejected: a LiveKit token cannot be revoked, and a track mute only affects subscribers, not the worker).
- **Lifetime:** seat-level, ending only on the facilitator's unmute — CHOSEN (owner decision 4); holder-connection-level like the participant's own mute (rejected: a refresh would undo a moderation mute); seat-level cleared when a different person takes the seat (rejected by the owner: it needs a new seat-handover log event and makes a restart disagree with a live session).
- **Who sees it:** the muted participant and the console only (rejected by the owner); every participant, by role label (CHOSEN, owner decision 5).

## 7. Tests and verification

Runtime unit and real-socket tests: `mute_seat` appends `facilitator.command` with `by` (a failed append fail-stops, C7); the seat stops recording at once and `voice_state` is re-sent; a `voice_line` for the seat is refused, including one in flight at the mute; refusals for voice off, an AI seat, an unknown seat and an ended session; accepted for a seat with no holder or a text-only holder; the participant's unmute refused with `muted_by_facilitator` and their mute accepted; a rejoin, a reissue and a different holder all keep the mute; a mute before the start is written after `session.started` and holds from the first turn (and is lost by a restart before the start, pinned as the residual); a `voice_line` that passed the recording check while a mute was queued is refused inside the engine mutex; a refused or failed-append mute is rolled back and an unmute applies only after its append; a fresh player join with no `lastSeq` sees the current mute in the snapshot and does not re-announce replayed mutes; a bot is not resumed by a `mute_seat`; no Game Master tick follows it; every participant's stream carries the mute and unmute by role label with no `by` and no person name; restart and replay rebuilds the state (the last command per seat wins); old-log tolerance (a log with `mute_seat` read by the resume code, control's readers and the evaluator input). Web tests: the new command kind (strict keys, a body `by` refused, the guard, the throttle, fixed sentences). Component tests: the console button, state words, announcements, the double press, and the participant page notice and disabled button. A real-store end-to-end through the speech worker's `voice_state` handling (a muted seat's frames are ignored and no audio file is written for it while muted). Mutation checks, each failing a named test: remove the facilitator set from the union, clear it on `release`, drop the `muted_by_facilitator` refusal, leak `by` or a person name to a player.

## 8. Left to the builder

Names inside the state (the command is `mute_seat`); the exact snapshot or peers-roster field for players; the throttle values; the wording of the notices (fixed sentences in `messages.ts`); the story, AC, TC and TASK ids.

## 9. Risks and residuals

Because everyone sees a mute (decision 5), a moderation mute is visible to the room; the copy is neutral and names only the role. A person who is muted can still talk in the room; the mute only stops it becoming game input (stated in the facilitator-facing copy). A line spoken before the mute stays in the sealed log, and the AI characters may already have answered it (owner decision 2). Without partials (A3b) the facilitator sees a side conversation only after its line lands or when they notice the speaking indicator; the mute is therefore most useful for the lines that follow. A muted seat that never had voice chosen stays muted if the person later opts in (by design: it can only stop recording).
