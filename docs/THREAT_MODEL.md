# Threat model (US-0017, US-0033, US-0013, EPIC-0002 slice 2a)

This is the threat model of the runtime server (`services/runtime`) for the text-based proof of concept, and of the participant web client (`apps/web`, [below](#the-web-client-epic-0002-slice-2a-us-0052-to-us-0056)). It says what the facilitator token and the connection limits protect, and, as exactly, what they do **not**. Read it before running the server on any network you do not fully trust.

## What is being protected

| Asset | Where it lives | Who may see it |
| --- | --- | --- |
| Role briefs and private facts | player `joined` message | that role only |
| Hidden facts, NPC goals and knowledge, Game Master reasoning, alerts, release suggestions (`gm.fact_earned`) | facilitator event stream | facilitators only |
| Whispers | facilitator and target role | those two |
| Participant names (terminal `--name`) | server memory, session log | facilitators (log) |
| Typed display names (web, US-0055) | `<id>.credentials.json`, `session.started` | the facilitator; other players of the session (peer roster) |
| Player credentials (US-0053) | salted SHA-256 in `<id>.credentials.json`; the plain value once to the BFF, then sealed in the participant's cookie | that participant's browser (sealed) |
| Consent records (US-0054) | `<id>.consent.json`, `session.started` | the facilitator; each player their own |
| Cookie sealing keys (`COOKIE_KEYS`) | the web server's environment | the operator |
| Session logs (`data/sessions/*.jsonl`) | disk | whoever can read the server's disk |
| Player join codes (US-0033) | the operator's screen once at start; salted SHA-256 hashes in `data/sessions/<id>.codes.json` | the operator, then each player their own role's code |
| Model API keys | `.env`, environment | the operator |

## Who might attack, and how

| Actor | Capability | Typical attempt |
| --- | --- | --- |
| LAN peer | can open a TCP connection to the port | join as facilitator, claim a player role (guess its join code), flood the server |
| A web page in a participant's browser | can open a WebSocket to `ws://<lan-ip>:8080` from the browser (cross-site WebSocket hijacking) | drive the server as the participant |
| A participant | already a legitimate player | escalate to facilitator, or claim another player's role, to read other roles' secrets, hidden facts and GM reasoning |
| A network observer | can read traffic on the path | read the token and all session text |
| A web page on another site | can make the participant's browser send requests to the web client | act as the participant through their cookie (cross-site request forgery) |
| Someone with a participant's cookie | a copy of the browser's cookie | take that participant's seat |

## What the facilitator token does

Set `FACILITATOR_TOKEN` (16 to 256 printable ASCII characters, no spaces) and the server requires it in `join_facilitator`:

- **Refused, not served.** A missing, empty, wrong or truncated token gets the same generic `unauthorized` error and the connection is closed (WebSocket code 1008) after the first failed attempt: frames that were already queued or keep arriving on that connection are discarded (none is processed), the socket is terminated shortly after. The address is charged for the refusal plus at most one more failure for that connection's dropped frames (and only if one of them really is a `join_facilitator` message), so a flood costs the server constant work. The reply does not say whether the token or the session id was wrong. A token longer than 256 characters is refused as a malformed message; a frame over 16 KiB closes the connection (1009).
- **Constant time.** Both values are hashed with SHA-256 and the digests are compared with `timingSafeEqual`, so neither the content nor the length of the real token leaks through timing.
- **Never logged or echoed.** The token is not in any log line, error, alert, event or message to any client. Startup errors about it name the variable and never show the value. The demo's checks (`F-28`, and `F-31` with `pnpm demo --security`) search logs, inboxes and narration for it.
- **Guessing is throttled.** More than 5 failed facilitator joins from one address within a minute block that address's new connections for a minute (HTTP 429). Behind a proxy this needs `TRUST_PROXY=1`, otherwise every client looks like the proxy.
- **Several facilitators.** Each facilitator connection needs the token (a co-facilitator is allowed).
- **It protects the facilitator stream and controls:** the full event view (whispers, NPC goals, hidden facts, GM reasoning, alerts) and the rights to start the session and send commands.

With `FACILITATOR_TOKEN` **unset the server stays open**: anyone who can reach the port can join as facilitator. The server prints one warning line at startup (it contains no secret) and tells each facilitator once, in the `joined` message (never to players). An EMPTY `FACILITATOR_TOKEN` in the real environment counts as unset, so it cannot switch off a token that `.env` holds; the real environment wins only when it has a value. The role id `facilitator` is reserved: a player cannot join as it and a scenario cannot define it. `./run.sh` generates a random token into a **new** `.env` only and never touches an existing `.env`. Refusing to start without a token on a non-loopback address is planned for a later release.

## What the player join codes do (US-0033)

When the server starts a session it creates one random join code per player role and a player `join` must present its role's code:

- **Random and typeable.** 12 symbols of Crockford's base32 (no I, L, O or U), shown as `XXXX-XXXX-XXXX`: 60 bits from `crypto.randomInt`. Case, spaces and hyphens are ignored when compared, and Crockford's look-alikes are folded (O to 0, I and L to 1). Anything outside printable ASCII is refused before case folding (Unicode upper-casing would otherwise map, for example, the long s `ſ` onto `S`). A client may send at most 64 characters (longer is a malformed message).
- **Shown once, stored as hashes only.** The plain codes are printed once on the server's standard output when they are issued (through a separate display, never the log lines, an error, an alert, an event or any client's messages), and exist nowhere else. The server keeps a salted SHA-256 of each code (salt per issue, bound to the role id) in memory and in `data/sessions/<id>.codes.json`, never in the event log. The demo's checks (`F-24`, `F-28`) search every log line, log file, codes file, inbox and line of narration for the codes.
- **Constant time, one generic answer.** The presented code is hashed the same way and the two 32-byte digests are compared with `timingSafeEqual`; a role that has no code (unknown, an AI character, `facilitator`, a prototype key) is compared against a dummy digest and refused, and an unknown session is checked against a module-level verifier that holds no codes (`JoinCodes.none()`), so it costs the same digest work. A missing or wrong code, an unknown or AI role and an unknown session all get the same `unauthorized` (code and message), so a refusal does not tell whether the role exists or is taken. Only someone holding the right code can learn that a role is taken (`role_taken`).
- **Refusals count against the limits.** A refused join is treated exactly like a refused facilitator token: one attempt per connection, the connection is closed (1008) and its queued frames dropped, and the failure is charged in the failed-login throttle. Since US-0052 a player's failures are counted per (address, role) (`player:<role>`, or `player:*` for a role id that is not a player role): more than 5 in a minute block that role from that address for a minute (the same generic `unauthorized`, without checking the code; attempts during the block do not extend it), while other roles, other addresses and the facilitator's handshake are unaffected. Each attempt also costs a connection under the connection caps and a message under the rate limit. At 5 guesses a minute per role, guessing a 60-bit code is hopeless. The other side: **typos still count, per address and role.** Where many clients share one address (NAT, a proxy, Docker Desktop) a handful of mistyped codes for one role block that role from that address for 60 s, a rejoining player of that role included. Behind a proxy you control, `TRUST_PROXY=1` gives each client its own address; otherwise wait out the minute.
- **Separate from the facilitator token and the reconnect token.** The facilitator joins with `FACILITATOR_TOKEN` (or openly when it is unset) and needs no code; a code never opens the facilitator stream and the token never opens a role. A player whose connection is still live can be replaced only with that connection's reconnect token (a rejoin with the reconnect token needs no code); a code alone cannot take a role from a live holder.
- **Restart.** The codes of a session that has started survive a restart (see [Logs at rest, the session lock and resume](#logs-at-rest-the-session-lock-and-resume-us-0018)): the hashes are read back from the codes file, the codes are not shown again, and the roles stay protected while nobody holds them. Every other start issues and shows new codes.

What the codes do **not** protect: anyone who is given (or overhears, or shoulder-surfs) a role's code can play that role while it is free; there is no TLS, so a code travels in clear text like the token (use a TLS reverse proxy off a trusted network); whoever can read the server's standard output (a terminal, `docker compose logs`, a log collector) at start sees every code; whoever can read the codes file can try to guess codes offline against the hashes (60 bits make that very expensive, and that person can already read the session logs, which hold everything the codes protect); and whoever can write the data directory can replace the codes file, like the log itself.

## Replay of missed events on rejoin (US-0013)

A `join` or `join_facilitator` may carry `lastSeq`, the seq of the last event the client saw; the server then sends the events after it that the viewer may see, right after `joined`. This is a new way to read the event stream, so it is held to the same rules as the live stream:

- **The same filter.** Each replayed event goes through the very function that filters live events (`viewFor`, default-deny: a new event type is invisible to players until it is explicitly allowed). A player is replayed only the events of the scenes it takes part in, injects addressed to it, pause and resume, and whispers addressed to it; never another role's whisper, NPC goals or knowledge, released hidden-fact text, Game Master verdicts, reasoning or `gm.no_verdict`, facilitator alerts or other participants' names (`session.started` is redacted as it is live). Join codes, the facilitator token and reconnect tokens are not events and never appear. A test compares, for every role and every possible `lastSeq`, the replay with what that role received live.
- **Authorisation first.** The replay is produced only after the join has passed every check (the join code or the reconnect token, the facilitator token, `role_taken`). A refused join gets its single generic refusal and nothing else (US-0033: no or a wrong code, an AI or unknown role, an unknown session, a wrong token all answer `unauthorized`). A `lastSeq` that is not a whole number from 0 is a schema error (`bad_message`) like any malformed field, also when the same message carries a wrong join code (a malformed message is rejected before any check, so this tells nothing about the role or the session); whether a `lastSeq` is past the end of the log is checked only after authorisation, so an unauthenticated client cannot learn how long the session is. (An authorised client learns it from its snapshot anyway.)
- **No gap, no duplicate.** The replay is read from memory and the client is subscribed to live events in the same synchronous step as its snapshot; the engine applies, retains and delivers each event in one synchronous step. A client that rejoins with its last seq therefore sees each event it may see exactly once, in order.
- **Bounded cost.** The engine keeps only the last 4096 events in memory (`MAX_RETAINED_EVENTS`; a restart refills them from the log, which is read once at start anyway). A rejoin never reads the log from disk, makes at most 4096 filter decisions and returns at most 1000 events and 256 KiB of JSON (`MAX_REPLAY_EVENTS`, `MAX_REPLAY_BYTES`). The join snapshot goes out in the same burst and a client with more than 1 MiB waiting in its send buffer is dropped, so the snapshot is serialised first and the replay gets only the room left: 1 MiB minus what is already buffered, the snapshot and a 64 KiB margin (at most 256 KiB). A rejoin with `lastSeq` is therefore never dropped where the same join without it is accepted; a long session's large snapshot simply leaves no room, and the replay is then `complete: false`. A client further behind gets `complete: false` and no events (never a partial list that would hide a gap) and relies on its snapshot. There is no per-address limit on the RATE of joins: each rejoin needs a new connection (one join per connection), and each new connection has its own message bucket, so the message rate limit does not slow a client that reconnects in a loop. What bounds it is the number of connections open at once (8 per address and 32 in all by default, plus the raw-socket caps and the join timeout) and, for a failed attempt, the failed-login throttle. A client holding a valid join code can therefore repeat joins as fast as it can open connections; each costs the bounded replay work above plus the snapshot, which every join already costs today and which is the larger part for a long session. A per-address join rate is a possible follow-up if that matters.
- **After `SESSION_START=fresh`.** The new log restarts at seq 1 under the same session id. A `lastSeq` from the old session that is past the new log's end is refused (`bad_message`); one at or below it is accepted and replays the new session's events after it that the role may see: the client only skips some early events of the new session (its snapshot still has the transcript), it never sees anything it may not see. Since slice 2a a player's `joined` carries the session's `logIdentity` when the runtime keeps seats, and the web client resets its view when it differs from the one in its cookie (US-0055); the terminal client does not use it.
- **After a restart.** Seqs come from the log and continue across a restart, so a client may rejoin with the seq it saw before the crash. The replay then includes events that reached the log but no client before a fail-stop (the log is the truth), and `session.resumed`; the restart alert stays facilitator-only.

What replay does **not** change: a client sees nothing it could not have seen live had it stayed connected. It does let whoever holds a role's join code (or the facilitator token) read up to the last 4096 events that role (or the facilitator) may see, not only what is said after they join; that is the same information the role's live connection received, and anyone who can read the session log has all of it anyway.

## Limits that apply to every client (token or not)

| Limit | Default | Setting |
| --- | --- | --- |
| Concurrent connections, all clients | 32 | `WS_MAX_CONNECTIONS` (1 to 10000) |
| Concurrent connections per address | 8 | `WS_MAX_CONNECTIONS_PER_IP` (1 to 10000) |
| Messages per second per connection | 5 | `WS_MSG_RATE` (1 to 1000) |
| Burst per connection | 20 | `WS_MSG_BURST` (1 to 10000) |
| Time to join after connecting | 10 s | `WS_JOIN_TIMEOUT_MS` (500 to 600000) |
| Messages waiting for the handler, per connection | 64 | fixed |
| Frame size | 16 KiB | fixed |
| Browser origins | none | `ALLOWED_ORIGINS` |

- Connection caps and the Origin check are applied at the HTTP upgrade, before a WebSocket exists: a refused client costs one small HTTP response (503 over a cap, 403 for an Origin that is not allowed, 429 for a blocked address).
- **Origin.** A handshake that carries an `Origin` header (a browser always does) is refused unless it is listed. The terminal client and the demo bots send none and are unaffected. This stops a web page in a participant's browser from driving the LAN server.
- **Rate limit.** Each connection has its own token bucket. Over the limit a message is dropped with `rate_limited`; three drops within 10 seconds, or more than 64 messages waiting for the handler, close that connection (1008). One client's flood does not use another's budget.
- **Join timeout.** A connection that does not join in time is closed, which also bounds idle and slow-drip ("slowloris") sockets. Raw TCP sockets are bounded too: at most twice `WS_MAX_CONNECTIONS_PER_IP` open sockets (idle or half-open included) per address (not applied behind `TRUST_PROXY=1`, where every client shares the proxy's address), an overall socket limit, and a 10 s header and request timeout (checked every second). One address that hogs its own sockets is refused or dropped; other addresses are unaffected. Connection caps are keyed by the full address; the failed-login throttle aggregates global unicast IPv6 (2000::/3) by /64 (one host owns a whole /64) but keeps full addresses for link-local and unique-local ones, which many people on a LAN share. The failed-login table is bounded (10,000 addresses per table, oldest evicted, expired entries swept at most once a second), including under forged `X-Forwarded-For` values; past 10,000 distinct addresses a block can be evicted early, which gives an attacker no new power (they could only have forged those addresses to begin with). A raw socket over the cap gets a short 503 before it is dropped.
- The per-address caps are weak where many people share one address (Docker Desktop, NAT, a proxy): raise them, or use `TRUST_PROXY=1` behind a proxy you control.
- **`TRUST_PROXY=1` is only safe when clients cannot reach the server directly**: otherwise anyone can forge `X-Forwarded-For` and dodge the per-address limits. The server warns at startup if `TRUST_PROXY=1` is combined with a non-loopback `RUNTIME_HOST`; **under the Docker Compose setup that warning is expected** (the container binds `0.0.0.0` and the safety comes from publishing the port on loopback only), so treat it as a reminder to check the `ports` line. Behind a proxy on the same machine bind `RUNTIME_HOST=127.0.0.1` (plain start) or, with Docker Compose, publish on loopback only (`ports: ["127.0.0.1:${HOST_PORT:-8080}:8080"]`; the container itself keeps `RUNTIME_HOST=0.0.0.0`, which the compose file pins).

## What the token does NOT protect

1. **No TLS.** The server speaks plain `ws://`. The token, every message and all session text travel in clear text, so anyone who can observe the network path can read the token and replay it. For anything beyond a trusted switch, put a TLS reverse proxy (for example Caddy or nginx) in front, serve `wss://`, bind the runtime to loopback with `RUNTIME_HOST=127.0.0.1` and set `TRUST_PROXY=1`. Do not put the token in a URL query: proxies log URLs. The client sends it in the first message.
2. **Player roles.** The token does not protect player roles: their join codes do (US-0033, above), and for a web seat its credential (US-0053, [the web client](#the-web-client-epic-0002-slice-2a-us-0052-to-us-0056)). A role held by a live connection can only be taken over with its reconnect token or its credential; a role is freed when its connection closes (including a crash or server restart), after which only someone with that role's code (or, for a web seat, its credential) can claim it.
3. **Logs at rest.** Session logs under `data/sessions/` hold everything the facilitator sees, including whispers, NPC internals and hidden facts if released, in clear text. The token does not protect them. Since US-0018 they are created owner-only (see [Logs at rest, the session lock and resume](#logs-at-rest-the-session-lock-and-resume-us-0018)); still protect the disk and the folder (and keep `.env` private: `run.sh` creates it with mode 600).
4. **The model provider.** Scenario text, prompts and dialogue are sent to whichever provider you configure. The token says nothing about that.
5. **Denial of service beyond the caps.** The limits bound what one address or connection can cost. A large botnet, a saturated network link or a host-level flood is out of scope.
6. **A participant who already holds the token**, or a facilitator machine that is compromised.
7. **Token theft from the environment.** `FACILITATOR_TOKEN` is readable by the user running the server, in the process environment and in `.env`. The terminal client takes it from the same variable, from `--token-file <path>` (read with a 1 KiB cap; a warning is printed if the file is readable by group or others) or from a hidden prompt, and never from the command line, because command lines show up in `ps` and shell history. The client warns once when it is about to send a token over plain `ws://` to a non-loopback host.

## Logs at rest, the session lock and resume (US-0018)

**What a log holds.** `data/sessions/<id>.jsonl` (and every rotated `<id>.<UTC time>.jsonl`) holds the whole session in clear text: every utterance, whispers, inject texts, AI character goals and knowledge (and hidden facts once released), Game Master reasoning, facilitator alerts and the participants' display names (`session.started.roles[].participantId`). It never holds the facilitator token, reconnect tokens, API keys or environment values. Because sessions now resume, logs live longer: delete them (rotated ones included) when you no longer need them; nothing deletes them for you.

**Protection on disk.**
- The data directory is created `0700`, and group and other permissions are removed from an existing one at start (never widened: a read-only directory stays read-only). Logs and lock files are created `0600`; an older, wider log is narrowed to `0600` when it is next written. The server warns when it cannot tighten the directory.
- Every append is followed by `fdatasync` before any client sees the event, so a crash or power cut cannot remove an event someone has already seen. Creating the log or lock and rotating a log also sync the directory.
- **Fail-stop.** If a write, an `fdatasync` or a tail repair fails, or the lock is lost, the log refuses every later append, the engine refuses every operation, the clients get a notice that is not a session event, and the process exits non-zero after a short drain for a supervisor to restart it. It never writes past an event it may not have applied. The event whose write failed may be on disk although no client saw it; the restart replays it (the log is the source of truth). On Linux a failed `fsync` may already have dropped dirty pages, so a later power cut can leave a hole in the log; the restart then refuses it as corrupt, and `SESSION_START=fresh` starts over (the refused log is moved aside, never deleted). The process exits non-zero for a supervisor to restart it (`restart: on-failure:5` in Docker Compose; `./run.sh --dev` does not restart).
- The server refuses a log or lock with more than one hard link (except a log whose second name is its own rotated copy, left by a rotation interrupted between link and unlink: that rotation is finished) or a pre-existing one owned by another user (chown it to the server's user; a file the server just created is not checked, for mounts that remap owners), and refuses to start when the data directory stays writable by group or others (it is tightened when it can be).
- Files are opened without following symbolic links (`O_NOFOLLOW`), and each decision about a file is made on the open descriptor (`fstat`), never on a path checked and then opened. A symlink in place of the log or lock is refused.
- There is no encryption at rest. Use disk encryption for anything beyond a demo.

**The session lock.** `<id>.lock` next to the log makes one server process the only writer:
- Created with `O_CREAT | O_EXCL | O_NOFOLLOW`, mode `0600`, holding the process id, host name and start time (never printed). The holder refreshes its modification time through the open descriptor every `SESSION_LOCK_STALE_MS / 6` (5 s by default) and checks that the path still names its own file; it checks again before every append, right before the bytes are written and after they are synced (a missing lock is re-checked once 50 ms later, since a competing starter can move it aside for an instant during a takeover race), and a lock that was removed or replaced makes the server fail-stop (above).
- Another start is refused while the lock is live, even with `SESSION_START=fresh`, so two processes can no longer rotate each other's log.
- Stale-lock takeover: a lock is stale when it has had no heartbeat for `SESSION_LOCK_STALE_MS` (30 s), or at once when it names this host and a process id that no longer runs, or this very process id while this process does not hold it (a restarted container reuses pids). The stale file is renamed aside under a random name, proven (device and inode, through descriptors) to be the file that was judged stale, removed, and the exclusive create retried; if another process replaced it in between, its lock is put back and the start is refused.
- Limits: process ids of another container cannot be checked, so **two containers sharing one data volume must have different host names** (Docker's default); on a network filesystem with unreliable `O_EXCL` or clocks the lock is best effort.

**The resume trust model.** On restart the server trusts its log: the state is rebuilt from it, nothing else. So **anyone who can write to `data/sessions/` can forge what a resumed session contains** (lines, goals, released facts, who said what): treat the directory like `.env`. The checks are about accidents, not attackers: a log that is corrupt beyond a cut-off last line, of a newer format, with an unknown event type, or written for another scenario (SHA-256 of the scenario as loaded and validated, in canonical JSON: an app upgrade that changes how a scenario loads can also refuse an in-progress resume; `SESSION_START=fresh` then starts over) is refused, never resumed "best effort", and never modified. Role claims and reconnect tokens are not persisted, so a restart behaves like a disconnect: every role is free again, but only with its join code, and the facilitator must present the token again.

**Join codes across a restart (US-0033).** The hashes of the player join codes live in `<id>.codes.json` next to the log, so the codes that were handed out keep working after a restart and are not shown again. The file is written only at startup, by the process that holds the session lock (it checks the lock right before the file is renamed into place), before the server accepts any connection: a new file is created exclusively (`O_EXCL`, `O_NOFOLLOW`, mode `0600`), synced, renamed over the old one and the directory synced, so a crash leaves either the old or the new codes, never half a file. It is read through one descriptor opened without following links and judged by `fstat` (a regular file, one link, owned by the server's user, at most 64 KiB; a wider mode is narrowed to `0600`). Only a RESUMED session (a log with a running session) keeps codes, and only when the file was issued for this session id, the same scenario (SHA-256, as in the log) and exactly the scenario's player roles; otherwise, or when it is missing (a log from before this version, or the operator moved it aside to issue new codes), new codes are issued and shown, with a warning that old codes no longer work. A start on a missing or empty log (nothing has happened in the session, or a played log was moved aside by hand) always issues and shows new codes: codes from an earlier start may never have been seen. If a start fails after it wrote new codes but before it showed them (the port is taken, a key is missing, a bad setting, the display itself fails), it removes the codes file again, under the lock, before it releases the lock, so the next start shows fresh codes instead of keeping ones nobody has. (The file is written before the display on purpose: a code on screen must already be durable.) Stale `<id>.codes.json.<hex>.tmp` regular files from a crash during a write are removed at start, under the lock (anything else with such a name is left alone). The lock check before the rename, and before a withdrawal, is synchronous: a lost, removed or replaced lock stops the write (the start fails) and leaves the file alone. **Known limitation:** if the process CRASHES (rather than fails) between writing re-issued codes for a resumed session and showing them, the next start resumes that session and keeps codes nobody saw, so nobody can join. Recovery: stop the server, move `<id>.codes.json` aside and start again, which issues and shows new codes. (A fresh or empty-log start is not affected: it always issues new codes.) A codes file that cannot be used (malformed, a link, another owner) is refused like a corrupt log: the server does not start, nothing is changed, and the message says to move the file aside to issue new codes. Starting fresh, or after an ended session, removes the old codes file BEFORE the log is moved aside, so a crash between the two can never let the old session's codes open the new one. The codes file plays no part in the fail-stop log: it is never written while a session runs. Clients that rejoin receive only what they may see (their scenes' transcript, and with `lastSeq` the events they missed, US-0013, through the same filter); the alert about the restart is facilitator-only.

**Seat files across a restart (US-0053, US-0054).** `<id>.credentials.json` and `<id>.consent.json` follow the codes file: the same writer (exclusive temp file, `0600`, rename under the lock, directory sync) and the same reader checks, written by the running server on every issue, revoke and consent change (not only at startup). They are kept on a resume only when the codes are kept and they match the session id, the scenario hash and, for consent, the current notice version (entries under another version are dropped); otherwise both are replaced with empty ones and a warning, and a start on an empty log or a fresh or ended rotation removes them with the old codes (removed before the log is moved; the old consent file is removed before new credentials are written, so a crash never pairs new credentials with stale consent). A malformed seat file stops the start without changing anything, like a malformed codes file. A resumed session counts as started: a seat is then taken only by the participant whose consent is recorded (seeded from `session.started` when the consent file lacks it), and a log written before the consent gate is not checked. Consequence for web players, by that rule and not exercised by a test: moving `<id>.codes.json` aside on a STARTED session gives new codes, but a web join with a new code carries a new participant id and is refused, so it does not bring back a web player who lost their cookie (see [the web client](#the-web-client-epic-0002-slice-2a-us-0052-to-us-0056)).

## Game Master release suggestions and GM_AUTO_RELEASE (US-0034)

A hidden fact may have an `earned_when` condition. The Game Master judges it on the dialogue and, when it holds, records the facilitator-only event `gm.fact_earned` that suggests `/release <role> <n>`. What protects it:

- **The fact never enters the Game Master's prompt.** The check holds the condition, the character's name, title and role id, the fact number and the current scene's dialogue. A model cannot reveal a fact it never saw, so a suggestion, its reasoning and every Game Master trace are free of fact text (the demo's `S-06` audits every captured Game Master prompt for every hidden fact).
- **The condition and the dialogue are untrusted data in the prompt.** Both are quoted (the condition as one JSON string with `<` escaped, each utterance as one JSON line) and the prompt says they are data, never instructions. The condition is scenario text (written by the operator) but is treated the same way.
- **A suggestion cannot be forged by typing.** The verdict path is the one of the exit conditions (US-0025): a fresh 64-bit nonce per evaluation in the system prompt only, and only a verdict object carrying it counts; quoted, echoed, nested, duplicated or conflicting verdicts are refused. The role id and the fact number come from the scenario, never from the model's reply, so the model's answer can only be true or false for the one fact that was asked about.
- **Only the engine's Game Master path writes the event.** The client protocol has no command for it (unknown commands are refused by the schema), the engine checks inside its mutex that the character is an AI character in the current scene, that the fact exists, has a condition, and is neither already suggested nor released, so a suggestion is made at most once per fact for the whole session. Players are denied the event (default deny) and their snapshot has no `factsEarned`.
- **It survives a restart without repeating.** The suggestion is an event in the session log, so a resumed session rebuilds `factsEarned` from it. (As for every other event, whoever can write `data/sessions/` can forge it: see the resume trust model above.)

What it does **not** protect against:

1. **Persuasion.** A participant can try to talk the model into judging the condition met, in the dialogue it reads. The nonce stops a typed verdict, not an argument. With suggestions only (the default) the cost is an alert the facilitator can ignore.
2. **`GM_AUTO_RELEASE=1`.** With this operator opt-in the Game Master releases the fact itself (`gm.fact_earned` with `autoRelease: true`, then the facilitator-only `npc.updated`). The release is recorded as the Game Master's action, not as a facilitator command, so the log shows who released it; but a participant who persuades the model then releases a fact without the facilitator. The setting is off by default, validated at start (`0` or `1`) and announced by a startup warning (a constant line). A crash between the two appends is completed on resume. Leave it off where a hidden fact matters.
3. **Model cost and delay.** At most `MAX_EARNED_CHECKS_PER_ROUND` (2) pending conditions are judged per evaluation round (least recently judged first, so each is still reached), and none in a round whose exit verdict came back true. One round is therefore at most (exit conditions + 2) Game Master evaluations, each bounded by `GM_TIMEOUT_MS` (with its retries and the one re-ask), so at most (exit conditions + 2) x `GM_TIMEOUT_MS` of waiting, whatever number of facts (up to 50 per character) carry a condition. A scenario author cannot make one round cost 51 evaluations.
4. **Event numbers show that something happened.** Every event has one session-wide `seq`, and players receive the events they may see with their real numbers. Each facilitator-only event therefore leaves a visible gap in a player's numbering: typically one per round for the `gm.decision`, two after the line that earned a fact (the `gm.decision` and the `gm.fact_earned`), three with `GM_AUTO_RELEASE` (plus the `npc.updated`). A participant who watches the gaps can tell that the Game Master recorded one more event after a line, and so probe an `earned_when` condition by trial and error. No fact text, condition or reasoning leaks this way, and the gaps also come from alerts, whispers to others and NPC updates. Numbering events per viewer would close it; that is a possible follow-up and is not done (the protocol is unchanged).

## Cheaper model calls: the Game Master window and the cached character prefix (US-0019)

**What the window shows.** A Game Master prompt (exit condition or earned_when check) no longer holds the whole scene. It holds, in the original order:
- at least the latest `GM_TRANSCRIPT_WINDOW` lines of the current scene (default 40, never fewer than `GM_EVERY_N_UTTERANCES`), widened to every line that arrived since the last prompt for the same condition that the model answered, also when the lines arrived while a slow evaluation was in flight; this widening stops at 500 lines, and beyond it the facilitator gets a warning alert with the number of new lines not shown;
- the scene's first 2 lines and the last 2 lines of each AI character in the scene, each with the line just before it (what the character was answering), kept outside the cut;
- one `{"omitted": n}` record wherever n lines are left out, and one system line with the numbers (how many lines of how many are left out). Nothing is summarised.

What is unchanged: each shown line is one JSON record with `<` escaped (a participant cannot write an omission marker or a second record: its text stays inside the `"text"` string of its own record); the nonce is only in the system prompt; the parser and the one re-ask are the same; no hidden-fact text and no participant name can enter (the window only removes transcript lines and adds counts). The window size, the lines a prompt covers and the alert count are taken from the same synchronous read as the prompt itself, so lines arriving while the alert is recorded are new for the next prompt, never dropped silently. Tests cover a forged record, a forged omission marker, a closing tag and a nonce-shaped verdict in kept lines.

**What the window cannot do (residual risk, accepted).** A line of a **player** that is not among the scene's first 2 lines can be pushed out of view by later lines: once a prompt of that condition has shown it, the next prompts show only what fits in the window. A player's objection can therefore be flooded out before the others propose and agree, and the Game Master may then see "stated AND agreed" with nothing disputing it: **a false exit that the whole-scene prompt would not give**. The message limits do not prevent it: with the defaults (`WS_MSG_RATE` 5 per second, `WS_MSG_BURST` 20, per connection) one player can send 40 lines in about 4 seconds, and two players at once in less. The same can hide a statement made long before the agreement that confirms it; that only gives a false (the safe direction). An **AI character's** objection stays in view until that character has spoken twice more; during a flood the character usually answers each flood line, so this protects only until its next two replies unless it repeats the objection. **Kept replies lose their wider context:** a kept AI character line is shown with the one line it answered, but whatever came between the kept groups is left out. A reply such as "Fine, approved" keeps the proposal it approved, yet a longer exchange it ended (several turns about proposal A) can be cut to its last turn, so after a flood a player's "So we agree on B" may still be read against a partial picture: a second, smaller way to a false true, which needs an agreement from the character that is ambiguous without the earlier turns plus a flood. The same mitigations apply. Mitigations: keep the window generous (40 is far above the 6 to 12 lines of the shipped scenes, about 25 live, so nothing is cut there), raise it for scenes that run long, and the facilitator sees every line and can end a flood. Earlier, with the whole scene in every prompt, this exit was not possible (but each evaluation's cost grew with the scene).

**A true verdict ends the round.** After one of a scene's exit conditions is recorded true, its other conditions and the earned_when checks are not judged in that round (the scene ends at the next tick). A stale verdict the engine refused is never recorded and does not count.

**The character prompt starts with a stable prefix that providers may cache.** It holds only scenario data of that one character that was already in every one of its prompts (instructions, persona, guardrails, voice): no goals, knowledge, hidden or released facts, scene, peers or lines (test TC-0022 and demo check S-06 assert it, byte for byte, through updates and scene changes). With Anthropic the cache breakpoint is placed at its end (never inside a UTF-16 surrogate pair); the cache is the provider's, scoped to your account, and holds nothing that was not already sent. Released facts stay in the last, uncached section, after the guardrails they override.

## Operating guidance

- Always set a token off a trusted network; use a TLS reverse proxy when the path is not trusted.
- Rotate the token by changing `.env` and restarting; a session in progress comes back paused and everyone (the facilitator with the new token) rejoins.
- Hand each player only their own role's join code, privately; note the codes when the server prints them (they are not shown again). To replace the codes of a running session, stop the server, move `data/sessions/<id>.codes.json` aside and start it: the session resumes with new codes.
- Keep `ALLOWED_ORIGINS` empty unless you serve a browser client. The web client does not need it: its BFF connects from the server side and sends no `Origin`.
- Web client: run the BFF only behind a TLS reverse proxy that replaces `X-Forwarded-For` with the client's address; bind the runtime to loopback (or a private network) with `TRUST_PROXY=1`; generate `COOKIE_KEYS` with `openssl rand -base64 32` per key, keep them out of the repository, add a new key in front to rotate and drop the old one only when its cookies may be lost (in 2a those players cannot rejoin until US-0058); set `PUBLIC_ORIGIN` to the exact origin the browser uses.
- Treat session logs, the data directory and `.env` as confidential; delete old logs.

## The review log and the attested participant channel (EPIC-0005, US-0041 to US-0044)

`pnpm moderate` keeps `review.jsonl`, an append-only log beside the reports. Its limits, stated plainly:

- **The hash chain is unkeyed.** It detects an edit in the middle of the log, a changed draft file and a cut-off last line. It does not detect cutting whole lines off the end (tail truncation) or rewriting the whole log with a valid chain. Anyone who can write the reports directory can do either.
- **Because the chain is unkeyed, the fold is the real check.** Every event is validated as it is folded, not only when it is written: every actor (a facilitator's `--by` and a participant's role and attesting facilitator are safe ids), the supersede marker (a directory name), export records (the current released version, a destination without control characters), carried copies (directly after the opener, of a carried type, naming a safe directory) and the drafts themselves (no duplicate criterion id, a well-formed per-role table). A hand edit that fails any of these makes the review refuse to load (exit 2) instead of rendering a forged name or record. Any unexpected failure while applying a command is reported as a bounded refusal that does not echo its input.
- **Supersede carries what a player said, never more than they saw.** Self-ratings, responses and disputes (with the facilitator's answers) move to the new review so an open dispute stays answerable; every subject starts in draft there, so nothing is visible to a participant until it is released again, and a player who already saw a release cannot make a new "blind" self-rating.
- **Released events do not commit to a content hash.** The log records that a release happened, not a hash of the snapshot text; the content is rebuilt from the log and the drafts.
- **The sibling-release check is not atomic across directories.** `open` refuses a re-run directory when a sibling directory of the same session was released, but two commands racing in different directories can both pass. A session-level lock on the parent directory would fix it. Per-directory locks on the siblings must not be used: `supersede` locks the old directory and then the new one, and sibling locks would add an order that can deadlock.
- **Self-assessment, responses and disputes are facilitator-attested, not participant-authenticated.** The log records `participant:<role>` and the name the facilitator passed in `--by`; nobody proves they are that participant. A participant sitting at the facilitator's machine shares the facilitator's OS user and can read every draft; the attestation is honest about that, and EPIC-0002 replaces it with real logins. Join codes are never taken on a command line.
- **Single-user CLI.** The commands assume one trusted operator on one machine with file access to the reports directory. `--by` is a label, `cat` of a report is not audited, and there is no protection against another local user who can write the directory.

## The web client (EPIC-0002 slice 2a, US-0052 to US-0056)

Slice 2a adds a participant web client: `apps/web`, a Next.js app whose server side is a backend-for-frontend (BFF), and runtime support for durable seats, recorded consent, display names and roster frames. A session is still started from the terminal. This section says what the new pieces protect and, as exactly, what they do not.

### Trust boundaries

```
browser --HTTPS--> reverse proxy (Caddy, TLS) --HTTP--> BFF (next start) --ws://, loopback--> runtime (TRUST_PROXY=1)
                                                                            terminal facilitator --ws://--> runtime
```

- **The browser never talks to the runtime.** It reaches only the BFF's pages and `/api/v1/` routes; `RUNTIME_URL` is never sent to it. The runtime must be reachable only by the BFF and the facilitator's own terminal (bind it to loopback or a private network): it runs with `TRUST_PROXY=1`, so anyone who can reach it directly can forge `X-Forwarded-For` (see [Limits that apply to every client](#limits-that-apply-to-every-client-token-or-not)).
- **The BFF is stateless about identity.** The sealed cookie carries the seat; the BFF keeps only open streams (one runtime WebSocket per open stream), a join throttle and a small in-memory list of sessions whose stream reported the end. A BFF restart therefore loses no seat (checked by the e2e flow and `pnpm demo --web` W-05), as long as `COOKIE_KEYS` is unchanged.
- **Confused-deputy rule.** The BFF acts on the runtime only for the participant named by the cookie, never for an identity in a request body, a query string or a header. A join is the one request that takes a role and a code from the body, and it can only seat the person who typed the code. Messages the BFF forwards on a participant's own stream connection are limited to `say`, `consent`, `withdraw_consent` and `leave` (an allowlist; a `join`, `join_facilitator`, `start` or `command` is refused before it reaches the socket). The `?session=` parameter of the stream route is only compared with the cookie's session; a mismatch is a 401. The BFF holds no facilitator token in 2a.
- **Request guards.** State-changing routes need `Origin` equal to `PUBLIC_ORIGIN` and the header `X-Requested-With: scenecoach` (a cross-site form or `fetch` cannot add it without a CORS preflight the BFF never grants). The stream route refuses `Sec-Fetch-Site: cross-site` or `same-site` and a foreign `Origin` (403), and answers 406 to a request that does not accept `text/event-stream` (a top-level navigation). Request bodies are read with an 8 KiB cap; the Next proxy (`src/proxy.ts`) does not run for `/api`, so Next does not buffer API bodies (it buffered up to 10 MB per request before this was fixed in review).
- **Player streams carry nothing a player may not see.** The BFF forwards the runtime's per-player frames (the runtime's default-deny `viewFor` decides) and picks the fields of `joined` one by one: no credential and no reconnect token reach the browser. `hub.runtime.test.ts` and `pnpm demo --web` W-07 scan every frame of a full mock session for facilitator-only event types and fields, the facilitator roster and commands, hidden facts, AI characters' goals and knowledge, other roles' briefs, facts and whispers, other players' consent, join codes in both spellings, credentials, reconnect tokens, cookies, addresses and participant ids, after proving each marker is present where it belongs. The scan finds only what is on its list: a new facilitator-only field must be added to both lists.

### The sealed cookie `__Host-scenecoach`

The cookie holds `{ sessionId, roleId, participantId, credential, logIdentity, expiresAt }`, sealed with AES-256-GCM (a fresh 12-byte nonce per seal, the key id as associated data, canonical base64url, at most 4 KiB). `COOKIE_KEYS` lists 1 to 8 `id:base64key` entries (32-byte keys), newest first: the newest seals, every listed key opens. Attributes: `HttpOnly; Secure; SameSite=Lax; Path=/`, no `Domain` (the `__Host-` prefix makes the browser enforce this), `Max-Age` from `COOKIE_MAX_AGE_HOURS` (default 12, 1 to 168); the expiry is also inside the sealed payload and checked on every request and, for an open stream, at each 15 s heartbeat (`event: expired`).

What it protects: page script cannot read it (`HttpOnly`; no browser code reads cookies or web storage, a source-rules test checks it); it is sent only over HTTPS (`localhost` excepted by the browser) and only to this host; a flipped byte, a relabelled key id, another key or an expired payload does not open (`seal.test.ts`); the credential inside is unreadable without a key.

What it does **not** protect:
- **It is a bearer token.** Whoever copies it (a shared computer left signed in, a stolen browser profile, malware) holds the seat until the participant leaves or withdraws, the session ends, or the cookie expires. The BFF keeps no revocation list; the runtime's credential is the only thing that can be revoked, and in 2a only the participant (leave, withdraw), the end of the session and a start that discards the seats with the old codes revoke it (facilitator removal is US-0059).
- **Whoever holds a `COOKIE_KEYS` key** can open any cookie sealed with it and read the plain credential, and can seal cookies. Treat the keys like the facilitator token: environment only, never committed (`.env.example` holds a placeholder). Removing a key from `COOKIE_KEYS` signs out everyone whose cookie it sealed, and in 2a those players cannot rejoin (below).
- **The cookie is not cleared at the moment the session ends.** An open stream cannot set a cookie after its headers are sent, so the BFF remembers (in memory, at most 1,024 entries) the sessions whose stream reported the end, and the next request clears the cookie and shows the end. The credential is revoked at the end anyway, so a leftover cookie opens nothing. After a BFF restart that memory is gone and such a reload reads "signed out" (the cookie is still cleared).
- **Cookie lifetime is not the session's end** in 2a (the BFF does not know it): it is `COOKIE_MAX_AGE_HOURS`.

### The player credential and the seat files

At the first web join by code (the BFF asks with `issueCredential: true`; terminal joins by code are unchanged) the runtime issues a 128-bit credential from a CSPRNG (32 hex characters), saves a salted SHA-256 of it with the display name and the log identity in `data/sessions/<id>.credentials.json` (mode `0600`, atomic rename under the session lock, before `joined` is sent), and returns it once in `joined.credential` to the BFF, which seals it into the cookie and closes that connection. Verification is constant time with a dummy digest for roles without a credential; input over 64 characters is refused. Once a role has a credential its join code no longer opens it. A drop never revokes; `leave`, a consent withdrawal and the end of the session do (the end latches, so no credential is issued again). A refused credential is counted under the throttle scope `cred:<role>`, never against the address as a whole. Consent is kept in `<id>.consent.json` (same mode and writer), with the participant who gave it. Both files are kept on a resume only when the join codes are kept, and discarded with the old codes otherwise; see [Logs at rest](#logs-at-rest-the-session-lock-and-resume-us-0018).

What the credential and the files do **not** protect:
- **A player who loses their cookie cannot rejoin in 2a.** The code no longer opens a role that has a credential, and per-role code reissue needs the control service (US-0058, AC-0308, slice 2b). A join whose response never reached the browser has the same effect. Before the start, any restart of the runtime issues new codes for everyone (the log is still empty, so the seats and consents go with the old codes). After the start the only workaround is a whole-session fresh start (`SESSION_START=fresh`): a new session with new codes, the old log moved aside.
- **Whoever can read the data directory** reads every typed display name (personal data) and the hashes (128 bits: offline guessing is hopeless); that person can already read the session log. Whoever can write it can replace the files, like the log.
- **Between the BFF and the runtime** the credential travels in clear text on `ws://`; keep that hop on loopback or a private network.
- **The terminal client** still joins by code and rejoins by code; nothing in this section changes it.

### Display names: peers see what was typed

A player types their own display name at the join (1 to 60 code points on one line; hidden, bidirectional and control characters stripped; a name with `\r`, `\n` or `\t`, or one that is empty after cleaning, is refused as `bad_message`, which the BFF answers as `400 bad_name` and charges to no throttle). The name is stored in the credentials file and in `session.started`, rendered only as text, never printed to the server's output or logs and never put in a model prompt (`roster.prompt-leak.test.ts`).

- **Peers now see typed names.** The peer roster frame lists each player seat with its name and whether it is ready; this is new (before 2a players saw no names). Peers can also tell that a seat is reserved but not connected (its name is listed while its credential exists). The facilitator sees every name, joined, consented and connected state.
- **Names are not verified.** Anyone with a role's code can type any name, a colleague's included. The facilitator should compare the roster with who is in the room.
- A player's copy of `session.started` carries no names and only their own consent (an allowlist).

### Client address, `TRUST_PROXY` and the per-role throttles

- **The proxy must always set a clean `X-Forwarded-For`.** The BFF takes the client address from exactly one `X-Forwarded-For` entry and normalises it (IPv6 in canonical form, IPv4-mapped IPv6 as IPv4). The reverse proxy in front of it must **replace** the header with that one entry (Caddy's `reverse_proxy` does this by default for clients outside its `trusted_proxies`; the repository has no proxy configuration yet, so check yours). An empty value, a comma-separated list (a proxy that appends instead of replacing) or something that is not an address gets a neutral 400. When the header is absent, `next start` fills it with the socket's address before any route runs (Next 16 `base-server.js`), so: **behind a proxy that does not set it, every client shares the proxy's address**, and then five wrong codes for a role from anyone block that role for everyone for 60 s and the per-address stream cap applies to all clients together; **with no proxy at all**, each client is keyed by its own socket address, but a client can also send its own one-entry `X-Forwarded-For` and so choose its key at the BFF and, through `TRUST_PROXY=1`, at the runtime. That lets one client dodge the per-address stream cap and spread its join guesses over many keys; it gains nothing against a 60-bit join code. Run the BFF behind a proxy that replaces the header; the e2e tests and the web demo send `X-Forwarded-For: 127.0.0.1` in its place.
- **The runtime trusts the BFF's header.** The BFF passes the address in `X-Forwarded-For` on its runtime connection and the runtime runs with `TRUST_PROXY=1`, so the runtime's per-address limits key on the real client. `TRUST_PROXY=1` also switches off the runtime's raw-socket cap per address, which is why the BFF has its own stream caps (below). Set `WS_MAX_CONNECTIONS` to at least the BFF's stream total plus the facilitators, and `WS_MAX_CONNECTIONS_PER_IP` to the most players expected behind one address.
- **Per-role throttles (US-0052).** The runtime counts failed logins per (address, scope): `player:<role>` for a wrong code for a known player role, `player:*` for any other role id, `cred:<role>` for a refused credential and the address-level scope only for a wrong facilitator token (handshake level, as before). More than 5 failures in 60 s block that pair for 60 s; attempts during a block do not extend it. Six wrong codes for one role therefore no longer lock out other roles or the facilitator behind a shared office address. The BFF keeps its own `JoinThrottle` with the same numbers per (normalised address, role): it checks it before contacting the runtime, validates the role id's shape and length (at most 128) before using it as a key, charges only the runtime's real `unauthorized` (not a blocked pair, a full table, a runtime 429 or an unavailable runtime), and answers every refusal with the same `401 join_refused`.
- **Saturation fails closed (ruling R20).** The BFF's throttle holds at most 10,000 (address, role) entries. When it is full and every entry is blocked it tracks nothing new and treats every untracked pair as blocked for 60 s, honest players included. One address can fill it with about 60,000 failed joins (10,000 role ids that pass the shape check, six failures each). This keeps memory bounded and stops a flood from evicting an existing block; the cost is that such a flood refuses every new join through the BFF for a minute. While the table is not full of blocks, eviction removes the oldest unblocked counter, so a flood can reset another pair's partial count (about 10,000 requests buy five more guesses for one pair). The runtime's throttle stays the authoritative limit either way.
- **Concurrent requests pass the BFF's pre-checks together.** The join throttle and the stream capacity are checked before an `await`, so N simultaneous requests can all pass them: for streams `hub.open` checks again and answers 503, closing the extra runtime connections; for joins up to N wrong codes per (address, role) can reach the runtime in one burst before the BFF's block applies. The runtime's own (address, scope) throttle is the real limit; the BFF's spares it the common case.
- **IPv6 is keyed per address, not per /64.** An IPv6 client usually controls a whole /64 and can rotate addresses inside it, multiplying its BFF join budget and stream cap. (The runtime's failed-login throttle already folds global unicast IPv6 by /64; its connection caps and the BFF do not.) Keying the BFF by /64 is a follow-up.
- **The console login throttle has a global bucket.** Without a TLS proxy a client chooses its own `X-Forwarded-For`, so the per-address login throttle (5 wrong secrets per minute) can be dodged by rotating it. Every wrong secret is therefore also charged to one address-independent bucket: more than 20 in 10 minutes block ALL console logins for 5 minutes. This caps secret guessing at about 240 guesses an hour whatever the addresses, at the price that an attacker can keep the facilitator locked out of LOGIN (a signed-in console keeps working). Deploy behind a proxy that sets the header, and use a long `FACILITATOR_SECRET`.
- The join code is passed to the runtime exactly as typed (up to 64 characters; the runtime normalises case, spaces and hyphens); the BFF neither normalises nor logs it.

### Server-sent events as a denial-of-service surface

Each open stream holds one runtime WebSocket, a heartbeat timer and buffers. Bounds:

| Bound | Default | Setting |
| --- | --- | --- |
| Streams in total | 200 | `WEB_MAX_STREAMS` (1 to 10000) |
| Streams per session | 64 | `WEB_MAX_STREAMS_PER_SESSION` (1 to 1000) |
| Streams per client address | 16 | `WEB_MAX_STREAMS_PER_ADDRESS` (1 to 1000) |
| Streams per participant | 1 (a second one supersedes the first) | fixed |
| Bytes queued for a browser that stops reading | 64 KiB in the response stream plus 256 KiB in the hub, then the stream is ended with `reconnecting` | fixed |
| Frames received before the stream listens (the replay) | 2,000 frames or 1 MiB, then the runtime socket is dropped | fixed |
| Request body | 8 KiB | fixed |

A stalled browser can therefore hold about 320 KiB of server memory before it is dropped, so 200 stalled streams cost about 64 MiB. Over a cap the stream route answers 503 before contacting the runtime. Each reconnect (the browser retries every 3 s after a drop) opens a new runtime connection, bounded by the same caps and by the runtime's own limits. A flood bigger than these caps is out of scope, as for the runtime.

### Known limits of slice 2a

- **A delayed older tab can end both tabs.** If tab A's `joined` reaches the BFF after tab B's and A's 4001 close arrives in a later socket read, both tabs end with "open in another tab". The window is narrow and a reload recovers. (The ordinary cases, double-click and two tabs, are tested: exactly one holds the seat and the older one stops without fighting back.)
- **The cookie is cleared on the absence of an error after `leave` or a withdrawal.** The runtime acknowledges neither, so the BFF clears the cookie when no error arrives within its 300 ms send window. A refusal that arrives later (for example `already_started` from a start that began at that moment) is missed: the cookie is gone although the runtime kept the seat and the credential, and the player is locked out until a per-role reissue (US-0058). Correlated acknowledgements in the runtime protocol would remove this.
- **Refusals that will not go away loop as Reconnecting.** A rejoin refused for a reason other than `unauthorized`, `session_ended` or `superseded` (for example `consent_required`, `bad_message` or `internal`) is sent to the browser as `reconnecting`, so the page shows the Reconnecting banner and the browser retries every 3 s until the cause goes away or the page is closed. Each retry is one runtime connection within the caps above. A later slice should send a final error for causes that are not transient.
- **A closed stream does not say why.** A non-200 answer (401, 403, 406, or a 503 from a full stream cap) makes the browser's EventSource give up without telling the page the status, so the page says "The connection to this session was closed. Reload the page; if that does not help, ask your facilitator." A reload works once a cap slot is free; a real `signed_out` event (a refused credential) keeps its own "ask your facilitator for a new code". A later slice could probe the status or answer a full cap as `reconnecting`.
- **`leave` after the start is refused** (`already_started`, ruling R13): a player cannot give up a seat mid-session; disconnecting is the only exit. Revisit with the facilitator console's "remove participant" (US-0059).
- **API responses carry no `Cross-Origin-Opener-Policy` or `Cross-Origin-Resource-Policy`.** Pages carry both; the `/api` routes get only the static headers from `next.config.ts` (`nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Permissions-Policy`), the JSON envelope's `Cache-Control: no-store` and `X-Robots-Tag`. Low impact (JSON with `nosniff`, no CORS); add them to the static headers later.
- **The CSP is nonce-only for inline scripts and styles.** `script-src 'self' 'nonce-…' 'strict-dynamic'` with no `unsafe-inline` (`unsafe-eval` only in development), `style-src 'self' 'nonce-…'`, `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`, a fresh nonce per request. Inline `style` attributes are therefore blocked: components must style with classes from the app's style sheets (a source-rules test enforces it). HSTS belongs to the TLS proxy, not the BFF.
- **The page timer uses the browser's clock** against the server's scene start time; a skewed clock shifts the shown time (clamped to the time box). It is display only.
- **Private pages are kept out of search engines, not out of reach.** `/join`, `/session`, `/report`, `/console`, `/admin` and `/api` send `X-Robots-Tag: noindex, nofollow` and are disallowed in `robots.txt`; join links carry no personal data. A join link without its code seats nobody.

### Consent notice versions

The runtime reads the notice from `consent/notice-<CONSENT_NOTICE_VERSION>.md` (default `v1`; 1 to 32 characters of `A-Z a-z 0-9 . _ -`; at most 4,000 characters, no control characters other than `\n` and `\t`) and does not start without it. A consent counts only under the server's current version and only for the participant who gave it.

**Status of v1:** `notice-v1.md` was reworded on 2026-10-28, before any real participant had agreed to it (it now says that other participants see your display name and what you say in shared scenes, and that the Leave button and `/withdraw` work only before the start). **Any edit after the first real agreement needs a new version.** The owner approved this wording of v1 on 2026-10-28.

**When to bump the version:** whenever the meaning of the notice changes (what is recorded, who sees results, which roles may be AI, how to leave). A typo fix that changes no meaning may stay on the same version, but the stored version then no longer pins the exact wording. **How:** add a new file `consent/notice-v2.md` (never edit a published version's file in place for a change of meaning; keep the old file in the repository as the record of what earlier participants agreed to), set `CONSENT_NOTICE_VERSION=v2` and restart. The Docker image copies `consent/`, so rebuild it. **What happens:** a restart before the start finds an empty log, so it issues new codes and discards every seat and consent anyway: everyone joins again and agrees to the new notice. A session that has already started keeps the consents recorded in its log for the participants who gave them, whatever version they were given under (ruling R15), so those participants can rejoin; a different participant cannot take a started seat.

## Facilitator console and control service (EPIC-0002 slice 2b-1, US-0057 to US-0059)

Slice 2b-1 adds a facilitator console to `apps/web`, a control service (`services/control`) that starts one runtime per session, and a small parent-only channel into the runtime. The terminal facilitator path is unchanged. This section says what the new pieces protect and what they do not. The live console (intervene, remove, end) and AI-filled player roles are slices 2b-2 and 2b-3 and will extend it.

### Trust boundaries

```
browser --HTTPS--> proxy --> BFF (next start) --loopback HTTP + x-service-token--> control service (127.0.0.1)
                                  |                                                  |  fork(), IPC (codes, ready, ended; reissue)
                                  +---- ws:// loopback, per participant / per console tab ---> runtime (one process per session)
```

- **The control service is a trust boundary.** It listens on 127.0.0.1 only and every request, including one for an unknown path, needs the `x-service-token` header (`LAUNCHER_TOKEN`, at least 32 characters, compared in constant time, one neutral 401 for a wrong or missing token). Anyone who holds the token can create sessions, read every session's facilitator token and port, reissue codes and restart sessions: treat it like the facilitator token (environment only, never committed, never sent to a browser). It is a bearer token on loopback HTTP, so any other local process of the same machine that can read the environment of the web server or the control service can use it. Bodies are JSON of at most 4 KB (refused before they are read), `scenarioId` must be a folder name in the allowlist built from `SCENARIOS_DIR` (a path-like id is refused before a file is touched), `MAX_SESSIONS` caps live sessions, and every error is the project envelope without a path, port, token or code (`services/control/src/api.ts`).
- **The runtime child gets an allowlisted environment** (`services/control/src/child-env.ts`): `PATH`, `NODE_*`, the provider keys and the NPC and Game Master settings the control service itself holds, plus values the service sets (`RUNTIME_HOST=127.0.0.1`, `RUNTIME_PORT=0`, `TRUST_PROXY=1`, `NO_DOTENV=1`, `CONTROL_MANAGED=1`, `SESSION_DATA_DIR`, a fresh `FACILITATOR_TOKEN`). `fork()` would otherwise hand the child everything, including `LAUNCHER_TOKEN` and `FACILITATOR_SECRET`; those two never reach a runtime. `GM_TRACE_FILE` is never set. Each runtime's stdout and stderr go to a per-session log file (mode `0600`, directory `0700`); join codes travel only over IPC, so the files need no redaction, and the control service never logs a code or a token.
- **Each runtime binds to loopback on a port the operating system picks.** The session-id-to-port mapping lives in the control service and the BFF, never in a cookie or a browser response. A local user on the same machine who can connect to a loopback port still needs the session's facilitator token (random, 64 hex characters, held in the memory of the control service, the web server and that runtime, never written to a file; the control service also passes it to its own child as `FACILITATOR_TOKEN` in the child's environment, so another process of the same user can read it from `/proc/<pid>/environ` or `ps eww`) or a join code to do anything.
- **The IPC channel adds no network surface.** The runtime talks to its parent over the `fork()` channel (`services/runtime/src/host/parent-channel.ts`): `codes`, `ready` and `ended` go up, and a reissue request comes down. The parent validates every child message against the same schema the runtime uses to send it (`services/control/src/protocol.ts`, tied to the runtime by a drift test), so a child cannot make the parent do more than the schema allows. A reissue exists only on this channel: there is no WebSocket message, HTTP route or command that reissues a code on the runtime, so a player or a compromised browser cannot call it. When the parent disconnects, the runtime stops and exits (with a hard-exit backstop), so a control service crash or restart leaves no orphan holding a session lock.

### The facilitator cookie and the shared-secret login

- **Purpose-bound seal.** `__Host-scenecoach-fac` is sealed with AES-256-GCM like the player cookie, but its purpose is part of the authenticated data (`apps/web/src/server/seal.ts`, `console-session.ts`). A player cookie therefore fails to open as a facilitator cookie and the reverse, and each route family accepts only its own purpose (a participant cookie on any `/console` route and a facilitator cookie on any player route are both refused). The player cookie format is unchanged.
- **Secret epoch.** The facilitator cookie carries a short value derived from `FACILITATOR_SECRET`; changing the secret makes every issued facilitator cookie read as signed out, with no revocation list.
- **Login.** `POST /api/v1/console/login` checks `Origin` (login CSRF), compares the secret in constant time, is throttled per address and fails closed when saturated (the same trade-off as the join throttle in the slice 2a section), and answers one neutral message for every refusal. The console is disabled with a generic message unless `FACILITATOR_SECRET`, `LAUNCHER_URL` and `LAUNCHER_TOKEN` are all set; the web server log says which are unset and a browser is never told. State-changing console routes need `Origin` and `X-Requested-With`, bodies are strict JSON of at most 1 KiB, and all `/console` and `/api/v1/console` responses send `X-Robots-Tag: noindex, nofollow`.
- **The facilitator name is an attested label, not an identity.** The shared secret identifies "a facilitator", not a person. The name is whatever the facilitator typed at login (cleaned, at most 60 code points), sealed into the cookie and used only as the `by` label for the audit trail and the consent rebind alert. Anyone with the secret can type any name, a colleague's included. It is never shown to participants.
- **One shared secret.** Every facilitator who knows it can open every session on that control service. There are no per-session owners or per-facilitator accounts in 2b-1.

### The BFF holds every live facilitator token

To read the roster and press Start, the BFF opens a short facilitator WebSocket per readiness poll and Start. It fetches `{ port, token }` together from the control service (`GET /sessions/:id/facilitator`), so it can reach every running session as its facilitator. This is accepted at the local stage because the BFF already holds the keys that open every participant cookie and a live runtime connection for every open stream; a compromised BFF could already read and act for all participants. The token is held in memory only, never written, never sent to a browser, and never put in a log. A facilitator socket sends no `X-Forwarded-For`, so a stale or refused token (counted by the runtime under one address-level scope) cannot block players from the same address; on a refused token the BFF fetches one fresh pair and retries once. The readiness answer carries role ids, joined, consented and connected flags and display names capped at 60 code points (the page renders them as text); it carries no port, token or launcher address.

### Reissue and the consent rebind (a facilitator-attested admission)

A code opens only a role that has no credential, so a reissue fixes an order (`services/runtime/src/host/reissue.ts`): write the new codes file first (an atomic write, the session lock checked), then revoke the credential (and withdraw or release the consent), persist the seats, kick the role's socket with close code 4002, swap the code instance in and reply with the code. Before the start the seat's consent is cleared, so the new person consents again. **After the start** consent cannot be given, and the BFF mints a new participant id at every join, so a plain reissue would never readmit a player who lost their cookie. A post-start reissue therefore **rebinds the seat's existing consent to the next participant who joins with the new code**. That is an admission decided by the facilitator, not by the participant: whoever has the new code is treated as the person who consented. The controls around it:

- Two facilitator-only alerts record it: one when the reissue is made (it names the role and the facilitator's label) and one when the next participant claims the seat. The consent entry changes hands only at the claim, which also stores the time. The alerts are appended only after the start; before the start an alert would make `engine.start` refuse the non-empty log (`services/runtime/src/host/session-host.ts`, `engine/consent.ts`).
- The marker uses a placeholder participant id that the server refuses when a client chooses it (`give`, `adopt` and the protocol schema), so a client cannot claim the rebind by naming it. The rebind is claimable only after the session has started, and a reissue while the start is in flight is refused, so no marker is left in a lobby that is still idle.
- A failed persist rolls the in-memory change back (credential, consent and the old seat), so a failed reissue never leaves the role open to the old code and to the new one at once, and the old holder is not locked out by a half-done reissue.
- The person who joins with the new code is shown the consent notice, read-only.
- The marker survives a restart: the consent store keeps a pending rebind under any notice version, and the resume path does not drop it.
- The code never appears in an alert, a log line or an error text.

What this does **not** protect: the facilitator is trusted to reissue only to the right person. A code sent to the wrong person admits them with the original participant's consent, and the log shows only that a reissue happened and by whom (as typed).

### Known limits of slice 2b-1

These are recorded in the SDD ledger (`.superpowers/sdd/2026-10-30-web-client-slice-2b1-control-plane/progress.md`) and are accepted for the local stage.

- **A crash can leave an undelivered code.** The write-first reissue order means a crash between writing the new codes file and delivering the reply leaves a code nobody saw while the old credential may still be seated. The recovery is another reissue of that role. A restart that keeps codes whose IPC delivery never completed likewise leaves a lobby nobody can join until a role is reissued (the readiness page says "Codes issued earlier are not shown again; reissue a role to get a new code").
- **A missing reply is an unknown outcome.** The control service treats a reissue request that gets no reply as "unknown, reissue again", never as success or failure.
- **Two control services on one data directory are unsupported.** The session list has no cross-process lock, so two processes can lose each other's updates and a second service would fight the first for session locks. Run one control service per `CONTROL_DATA_DIR`.
- **`HOME` and `ALLOWED_ORIGINS` are not passed to children,** and `WS_MSG_RATE`, `WS_MSG_BURST` and `WS_JOIN_TIMEOUT_MS` are not either. The runtime uses its defaults for them. The BFF's server-side WebSocket sends no `Origin`, so `ALLOWED_ORIGINS` is not needed for it.
- **`NODE_OPTIONS` is copied through the `NODE_*` allowlist,** so an operator who sets `--inspect` for the control service gives every child an inspector port. It is operator-trusted; do not set it in production.
- **A facilitator-socket refusal for the throttle (429) is reported as "unavailable"** rather than as a throttle, and the readiness poll backs off.
- **An ended or stopped session shows players "Reconnecting".** A player whose session has ended or stopped sees the Reconnecting banner every 3 s indefinitely (one launcher lookup per retry per tab) until the end-of-session screens of slice 2b-2 map the state to the final "ended" message. A player whose code was reissued (close code 4002) is told to ask for a new code and is not reconnected.
- **Every join and stream costs one uncached launcher lookup.** The control service is on loopback, so the cost is small, but it makes the control service a dependency of every player request in launcher mode.
- **Console pages show join codes.** Codes live in page memory only (never storage or the URL) until "I have copied the codes"; a browser extension or a shoulder surfer can read them while shown. Every `/console` page is served with `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` (the pages are `force-dynamic`; checked on a real `next start` response), so a cached or restored copy is not kept.
