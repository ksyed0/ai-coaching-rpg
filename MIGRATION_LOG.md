## 2026-10-07: replay-from-seq on rejoin (US-0013)

- **Files:** `services/runtime/src/host/protocol.ts` (`lastSeq` on `join` and `join_facilitator`, `ReplaySummary` on `joined`), `host/ws-server.ts`, `host/session-host.ts` (`replayFor`, `MAX_REPLAY_EVENTS`, `MAX_REPLAY_BYTES`), `engine/recent-events.ts`, `engine/session-engine.ts` (`eventsAfter`), `cli/commands.ts`, `cli/client.ts`, `cli/render.ts`.
- **Applies to:** every future client (web lobby EPIC-0002, voice EPIC-0003, 3D EPIC-0004). The terminal client has it; nothing else exists yet.
- **What a client must do.** Keep the seq to rejoin with and send it as `lastSeq` when it rejoins, in the same `join` / `join_facilitator` it sends today (join code or reconnect token or facilitator token unchanged). Old value: no field, the client got only its snapshot (its scenes' transcript). New: the `joined` reply carries `replay: { afterSeq, toSeq, events, complete }`; exactly `events` event frames follow at once, before any live event, holding the events with seq in `(afterSeq, toSeq]` its role may see, oldest first. `toSeq` equals the snapshot's `state.lastSeq`; every later frame has a higher seq. Render the snapshot's history only up to `afterSeq` (later lines arrive as replayed events) and drop any event frame whose seq is not above the last one received (the server sends none; it is a guard). Tracking rule: the seq to rejoin with is: after a `joined` WITHOUT a replay or with `complete: false`, that snapshot's `state.lastSeq`; after a `joined` with a complete replay, its `afterSeq` (NOT `toSeq`: the replayed frames have not arrived yet), then the seq of each event frame as it actually arrives. A client that drops in the middle of a replay thus rejoins from the last replayed event it really got and loses nothing. A facilitator client should also name the text of a hidden fact whose `release_hidden` command is in the replayed range (its snapshot already lists the fact as released, so the replayed `npc.updated` adds nothing new).
- **`complete: false`** (`events: 0`): the client was further behind than the server replays (older than the last 4096 events, more than 1000 events or 256 KiB for its role, or more than fits in the 1 MiB send buffer beside its snapshot: a long session's large snapshot leaves less room). Treat the snapshot as a full resync and tell the user that earlier injects and whispers are not shown.
- **Errors.** A `lastSeq` that is not a whole number from 0 to 2^53-1 is `bad_message` (before authentication); one past the session's last event is `bad_message` once the join is authorised (nothing claimed): rejoin without `lastSeq` (it happens after `SESSION_START=fresh` started a new log under the same session id). A `lastSeq` from before a fresh start that is at or below the NEW log's head is accepted and replays the new session's events after it that the role may see (never anything it may not see; the effect is only that the client skips the new session's first events, which its snapshot transcript still shows). A log identity in `joined` that a client could compare is a possible follow-up. A malformed `lastSeq` is `bad_message` even together with a wrong join code (the message is rejected as malformed before the code is checked, and nothing about the session is revealed). A refused join (`unauthorized`, `role_taken`) gets nothing else.
- **Restart.** Seqs come from the session log and continue across a restart, so the same `lastSeq` works after the server restarted; players are then replayed `session.resumed` (the restart alert is facilitator-only).
- **Still to do per platform:** the web lobby (EPIC-0002) must persist the last seq across a page reload (for example in `sessionStorage`) and reconnect automatically; the terminal client exits on a drop and prints `--last-seq <n>` instead of reconnecting by itself.
